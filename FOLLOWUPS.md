## Bugs

- **`PATCH /stock/:id` can overwrite a sale's stock change (lost update).** `StockService.update` reads the Stock row without a lock, sets the new values on the entity and saves it, outside any transaction that locks the row. A sale completing (or a void, a trade-in, a phone purchase) between that read and the save is overwritten: the admin's absolute `quantity` lands on top of the decrement, and a `manage_stock` or `min_quantity` edit writes back the stale `quantity` too if TypeORM includes it in the UPDATE. It can't deadlock (one row), so P7 step 0c left it alone. Fix: do the update in a transaction that locks the row through `lockInventoryRows` (planning doc section 8 P7-25), and decide whether an admin edit should be an absolute set or an adjustment (the `stock_adjustments` table under Deferred infrastructure). _[Phase 6.4 P7 step 0c recon]_

- **API rate limit is per IP, so tills on one shop network share it.** **Priority: medium. Blocks R1 at 3+ concurrent tills.** `ThrottlerModule` (`backend/src/config/throttle.ts`) applies 10 req/s and 100 req/min per route and per client IP: the throttler's default key is the route handler plus the IP, so each endpoint has its own allowance. All tills behind one shop router share a single public IP and therefore share each route's allowance. A busy scan calls by-barcode, addLine and stock once each, so about 100 scans a minute across a shop's tills reach 100/min on each of those routes and start getting 429s on scans and line edits. Found in Phase 6.4 P1 E: one cashier's terminal hit the limit while reloading the page repeatedly. Fix: key authenticated routes by user instead of IP, by subclassing `ThrottlerGuard` and overriding `getTracker()` to return the user id. `JwtStrategy.validate` maps the token's `sub` to `req.user.id`. and fall back to the IP for anonymous routes. Keep `/auth/login` keyed by IP, since it's anonymous; it also has its own limit (`LOGIN_THROTTLE_*`, `docs/backend/auth.md` "Login rate limit"); see "Login has no per-account lockout" under Go-live setup. Sketch:

  ```ts
  @Injectable()
  export class UserThrottlerGuard extends ThrottlerGuard {
    protected async getTracker(req: Record<string, any>): Promise<string> {
      return req.user?.id ? `user:${req.user.id}` : `ip:${req.ip}`;
    }
  }
  // app.module.ts: { provide: APP_GUARD, useClass: UserThrottlerGuard }
  // req.user exists only if JwtAuthGuard (APP_GUARD in AuthModule) runs before
  // this guard (APP_GUARD in AppModule). Verify the order, or move both into one
  // module in the right order, before relying on it.
  ```
  _[Phase 6.4 P1]_

- **Add-time trade-in errors still name the product by UUID and their 409 has no IMEI.** `SalesService.addPayment` → `assertTradeInPaymentReferencesValid` still says `Trade-in product <uuid> not found or inactive`, and its "IMEI already exists in inventory" 409 carries `existing_unit` but not the `imei`. #32 fixed only the complete-time versions (E9–E11, planning doc P5-2). The POS words the 409 itself (by `existing_unit.status`, P4-7), but shows the 400 as sent, so a cashier who picks a product that was deactivated meanwhile sees a UUID (rare: the picker lists active products only). Fix: the same treatment as #32 (product name in the message; `imei` in the 409 body), with the e2e assertions updated. _[Phase 6.4 P5 recon]_

- **`updated_at` not bumped on QueryBuilder `.update()`.** `StockService.decrementForSale`/`incrementForReversal` and `ProductUnitsService.markSoldForSale`/`markAvailableForReversal` use `manager.createQueryBuilder().update(Entity).set({...})`, which bypasses TypeORM's `@UpdateDateColumn` auto-bump. `updated_at` stays at the row's creation timestamp even after status/quantity changes. Cosmetic — no data-integrity impact — but breaks any "recently changed" ordering. Fix: add `updated_at: () => 'now()'` to each `.set()` clause, or install a Postgres trigger. _[Phase 6.3 Stock, Slice E PU]_

- **Customer can be cleared from a DRAFT that has TRADE_IN payments.** `addPayment` requires `sale.customer_id` for TRADE_IN, but `PATCH /sales/:id` with `customer_id: null` still succeeds afterwards. `completeSale` catches it with a 400 before calling `createForTradeIn` (PhonePurchase needs a customer), so there is no data risk — but the error surfaces late. Fix: in `SalesService.update`, reject clearing `customer_id` when the sale has any TRADE_IN payment. _[Slice G]_ **Resolved** — shipped in #22 (also covers customer reassignment).

- **PERCENT discounts don't always round half-up.** `SalesService.resolveDiscountAmount` (`backend/src/sales/sales.service.ts:1548`) computes `roundToCents((lineSubtotal * value) / 100)` in floats. The `+ Number.EPSILON` nudge in `roundToCents` (`:1486`) only rescues values below ~1, so exact half-cent results often round down: 50% of 4.35 should be 2.18 (half-up) but stores 2.17. No DB constraint is violated and the error is ≤1 cent in the customer's favour. Fix: compute in integer cents (`toCents(unitPrice) * quantity * pct`, half-up on the exact value). That changes stored `discount_amount` for some existing inputs, so this behaviour change needs its own review. Found in the sales money audit alongside the payment-remainder fix. _[Phase 6.3 Slice D]_ **Resolved** — shipped with P5-19/P5-20 (`percentOfCentsHalfUp`; line money in integer cents).

- **`GET /sales` reads a date-only `from` / `to` as a UTC day, not a Colombo day.** `SalesService.findAll` compares `created_at` with the raw `from` string (the DB session time zone, not set in `typeorm.config.ts`, so presumably UTC) and `normalizeToUpperBound` turns a date-only `to` into the next UTC midnight. A Colombo day starts 5h30 earlier, so `from=2026-10-21&to=2026-10-21` misses sales made 00:00–05:30 Colombo time and includes the next night's. The POS (P6-2) sends explicit `+05:30` timestamps and isn't affected. Fix: treat date-only bounds as Asia/Colombo days, or reject date-only values; either changes the API's meaning, so it needs its own review. _[Phase 6.4 P6 recon]_

- **A route that demotes a user to cashier or deactivates one must clear the approval PIN first.** `CHK_users_approval_pin_role` (Phase 6.4 P6-15) rejects a cashier holding an approval PIN, so such an UPDATE fails unless the PIN fields are cleared in the same statement. Today no route changes a role (`UpdateUserDto` omits it) and `UsersService.deactivate()` (no route) already clears them. When the Phase 6.8 user screens add role changes or deactivation, set `approval_pin_hash`, `approval_pin_set_at` to null, `approval_pin_failed_attempts` to 0 and `approval_pin_locked_until` to null in that update (docs/backend/approvals.md, Lifecycle). _[Phase 6.4 P6 0b]_

- **`toSafeUser` removes secret user fields by name.** `toSafeUser` in `backend/src/users/users.service.ts` drops `password_hash` and the approval PIN's hash, count and lock from the plain objects `UsersService` returns (plain objects skip `ClassSerializerInterceptor`, so `@Exclude` doesn't apply to them; that gap leaked the PIN count and lock until Phase 6.4 P6 0b). Any new secret column on `users` must be added there too. Alternative: have `UsersService` return entity instances so `@Exclude` applies. _[Phase 6.4 P6 0b]_

- **Customer search doesn't escape LIKE wildcards.** `CustomersService.findAll` builds `%${query.search}%` unescaped (`backend/src/customers/customers.service.ts:88`), so a search for `%` or `_` matches every customer instead of the literal character. The product search and the sales `q` (P6-3) escape `\`, `%` and `_` first. Fix: the same escape here. _[Phase 6.4 P6 recon]_

- **Phone search doesn't normalise `+94` to `0`.** Customer phones are stored as `0XXXXXXXXX` (`normalizeSlPhone` on create/update), but the customer search and the sales `q` (P6-3) match the typed text as a substring, so `+94771234567` or `94771234567` finds nothing while `0771234567` does. Fix: when the search text normalises to a valid SL phone, match the normalised form too. _[Phase 6.4 P6 recon]_

- **Invoice and return numbers are dated by the app clock, `completed_at` by the database clock.** `SaleNumberCountersService.currentColomboDate` takes the Colombo date from luxon on the app server's clock, while `completed_at` (and `voided_at`, `sale_returns.created_at`) is the database's `now()`, the transaction start. Around midnight, or with clock skew between the two servers, a sale can be numbered `INV-<next day>` with a `completed_at` on the day before (or the reverse), and the same for `RET-` numbers. P9's daily balance groups by `completed_at` (planning doc section 8 P9-4, P9-21), so a day summary could list such a sale under the other day's number. Low severity: the shop doesn't trade past 12 AM. Fix: take the counter date from the database in the same transaction (`(now() AT TIME ZONE 'Asia/Colombo')::date`). _[Phase 6.4 P9 recon]_

- **Voided-trade-in stock shortage 409 names products by UUID.** `StockService.decrementForVoidedTradeIn` throws 409 `Insufficient stock for voided trade-in at product <uuid>, branch <uuid>…`. It is an integrity condition (should not happen), and the POS shows it as "Couldn't void. Nothing was changed." (P6-11), but the message is unreadable in logs and Swagger. Fix: name the product and the IMEI. _[Phase 6.4 P6 recon]_

- **`AuditLogInterceptor` pre-fetch runs before `ParseUUIDPipe`.** Malformed UUIDs on `PATCH`/`DELETE` routes surface as 500 (interceptor tries to fetch by malformed id) instead of 400 (pipe should reject first). Cosmetic. _[Phase 6.3]_

- **Schema drift between entities and migrations.** `migration:generate --dryrun` on develop prints about 80 lines of drift: hand-named FKs, CHKs and indexes in the migrations that the entities don't declare (or declare with TypeORM's generated names), across most tables. Nothing is wrong at runtime (`synchronize` is off), but a generated migration would drop and recreate constraints. Align the entities, or document the drift, before anyone generates migrations. The buy-back PR removed the `product_units.imei` part. Phase 6.4 P7 step 0a named the three `product_units` CHECKs on the entity as the migrations do (`CHK_product_units_status`, `CHK_product_units_buying_price_nonneg`, `CHK_product_units_selling_price_nonneg`), so they and `uq_product_units_imei_live` no longer show in the dry run; `product_units` still shows its three hand-named FKs (`FK_product_units_product` / `_branch` / `_phone_purchase`, `ON UPDATE CASCADE`) and the indexes `idx_product_units_product_branch_status` and `idx_product_units_phone_purchase_id`, which the entity doesn't declare. _[buy-back PR, P7 recon, P7 step 0a]_

- **Access tokens stay valid after logout or reuse-detection revocation.** `JwtStrategy.validate` (`backend/src/auth/strategies/jwt.strategy.ts`) re-reads the user and checks only `is_active`; it never looks at `refresh_tokens`. Logout and the "all sessions revoked" response to a replayed refresh token revoke refresh tokens only, so an access token already issued keeps working until its JWT expires (`JWT_ACCESS_EXPIRES_IN`, default 15 minutes). Logout clears the browser's cookie, but a copied token still works for that window. Fix: carry a session id in the access token and reject it once that session is revoked, or accept the window and keep access tokens short. _[PR #65 audit]_

## Test-environment friction

- **The global rate limit isn't configurable, so e2e suites sleep to stay under it** (formerly "Login throttle limit is not env-driven"). The global `short` and `long` limits in `backend/src/config/throttle.ts` are hard-coded at 10 req/s and 100 req/min, counted per route and per client IP, and every e2e request comes from the one test address, so a spec's busiest routes (login above all) reach them. The login route's own limit is configurable (`LOGIN_THROTTLE_LIMIT`), and `test/load-test-env.ts` raises it for e2e runs; the global limits are not. The specs stay under it with fixed sleeps: before each login, 110 ms in most specs and 500 ms in `sales`, `approvals`, `inspection-status`, `cash-days`, `cash-days-enforcement` and `returns` (the sales helper was raised from 110 ms during Slice E when the spec hit 108+ tests); and 650 ms before every request in `null-fields`. Every additional e2e test pays that sleep. Fix: read the throttle limits from configuration so the test environment can raise them, keep the production values, and drop the sleeps. That would shorten the sales e2e run substantially (an unverified estimate from when this entry was written: ~90 s → ~30 s). _[Phase 5, worsened Slice E]_

- **`customers.e2e-spec.ts` `loginAndGetCookies` expects 201.** `/auth/login` returns 200 (`@HttpCode(HttpStatus.OK)`). Helper needs verification; if it's currently coincidentally passing due to earlier throttle 429s masking things, it'll bite later. _[Slice A]_

- **Audit log write teardown noise in e2e.** After test suite finishes, `AuditLogInterceptor.writeAuditLog` occasionally logs "Connection terminated" errors when the app's teardown closes the pool before an in-flight audit write completes. Non-blocking, but noisy in CI output. Louder now with Slice E adding more audited endpoints. _[Phase 6.3, worsened Slice E]_

- **Intermittent `deadlock detected` in `products.e2e-spec.ts`.** Seen once in a full `npm run test:e2e` run during Slice G: `POST /products › auto-generates SKU and barcode` failed with `40P01` on the `products` INSERT, alongside an `AuditLogInterceptor.writeAuditLog` error. Passes on rerun, and the suite passes in isolation. **Also seen in `sales.e2e-spec.ts`** (full run during Phase 6.4 P7 step 0a): a test timed out at 5 s (`complete › rejects an unknown code as a line warranty`), then the next test's `truncateAllTables` in its setup failed with `40P01`; the spec passed 204/204 on its own and the full suite passed on rerun. **Also seen in `stock.e2e-spec.ts`** (2026-10-25, full run during Phase 6.4 P9 backend 0b): `PATCH /api/v1/stock/:id › cashier is forbidden from updating stock` failed in its `beforeEach` with `40P01` from `truncateAllTables` (`test/setup.ts:55`); the spec passed 10/10 on its own and the full suite passed on rerun. Likely the same fire-and-forget audit write racing `truncateAllTables`; the 50ms pre-truncate sleep in `test/setup.ts` isn't always enough. Fix: have the interceptor track in-flight writes and await them in teardown/truncate, rather than sleeping. _[Slice G]_

- **`SaleNumberCounter` real-DB concurrency test is mocked.** No real-DB test exercises the counter under concurrent pressure. Add one if a race bug ever surfaces. _[Phase 6.3]_

- **Four `cash-days-enforcement.e2e-spec.ts` tests predate the `OPEN_SALES` close rule and fail.** "close racing a sale" (close first; sale first, the dialog's figures from before the sale; sale first, the close waits for the sale) and "refused, nothing changed › complete on a closed day". Each seeds a paid DRAFT and then closes the day expecting the close to succeed or to wait on a lock, but since #53 (P9-12, `docs/backend/cash-days.md`) close refuses with 409 `OPEN_SALES` while any DRAFT with lines or payments changed since the day opened exists, so the close never waits (the lock-waiter polls time out) or returns 409 instead of 200. The spec was last changed in #52, before the rule. The rule is correct and stays. Fix: redesign the scenarios for it, e.g. race close against a sale that is already completing (past the `OPEN_SALES` check) rather than an idle draft, and test the closed-day refusal on a sale that was completed or discarded before the close; keep the `OPEN_SALES` refusal itself covered. _[e2e product-tracking seed fix]_

## Deferred features

- **Admin endpoint to update `ProductUnit.selling_price` post-intake.** The "price later" workflow (Cashier Option C from Slice D) requires this. Currently there's no way to set the per-unit price after intake if the cashier left it null. _[Slice D]_

- **`ProductType.USED_PHONE` enum value.** Add a specific type for used phones and gate PhonePurchase intake on it, so accidental intake of new-retail products fails cleanly. _[Slice D]_

- **No supplier stock intake with IMEIs (new serialized phones can't be sold in-house).** **Priority: high — its own phase after 6.4 P5.** ProductUnit rows are created only by `POST /phone-purchases` (buying from a customer, `phone-purchases.service.ts` `create`) and by trade-ins at `completeSale` (`createForTradeIn`). `PATCH /stock/:id` changes the quantity only and creates no units, and a serialized in-house sale line needs an existing IN_STOCK unit for its IMEI (`resolveInHouseSerializedLine` → 400 "IMEI '…' is not in stock"). So a new phone from a supplier can't be rung up as a serialized line; today's workarounds (mark it non-serialized and lose the IMEI, a fake "supplier" customer on `POST /phone-purchases`, or the external-supplier line mode) are all wrong. Needs a supplier-receiving endpoint that creates N IN_STOCK units with IMEIs and cost, increments stock, and links the supplier, plus its screen. The same phase handles **returning faulty phones to their supplier** (a customer return found faulty at inspection, P7; planning doc §8 P6-24), which needs that supplier link. Until then a faulty returned phone stays in `INSPECTION` on P7's Phones to check list (P7-7); this phase adds the faulty outcome (a status or a supplier-return record) and takes it off that list (see "Faulty returned phones" below). Now part of "Go-live: inventory intake" under Go-live setup. _[Phase 6.4 P4 recon, extended P6 planning, P7 planning, P7 G]_
- **Faulty returned phones: "Mark faulty" and a status of their own.** P7 has only one outcome for a returned phone on Phones to check: **Passed: back to stock**. ## Go-live setup

- **Create the common used-phone catalogue models before go-live.** A trade-in or phone purchase needs an existing, active, serialized product at the branch, one per model/storage (e.g. "Used iPhone 12 128GB"), and only admins can create products. If the customer's model is missing, the cashier is stuck (the POS shows "No used-phone product for this model. Ask an admin to add one."). Seed the models the shop commonly takes in (`is_serialized = true`, `phone_condition = USED`) at each branch, labelled the way the cashier will search for them ("Used iPhone 12 128GB"). Also create one fallback per main brand, **"Used phone – <brand> (other)"** (e.g. "Used phone – Samsung (other)"), so a trade-in of an uncommon model can still be recorded; an admin can add the proper model later. The customer also needs an NIC on file for a trade-in or phone purchase (P4-13, #29). _[Phase 6.4 P4 planning, revised P4 build]_

- **Fill in each branch's address and phone before go-live.** The printed receipt (Phase 6.4 P5) takes its header from the sale's branch: name, address and phone. `address` and `phone` are nullable, and the receipt skips a null one, so a receipt from a branch without them has no address or phone. There is no branch admin screen in the frontend; set them with `PATCH /branches/:id` (admin) via Swagger or a seed. The shop name and footer text live in `frontend/src/constants/receipt.js` (P5-14). _[Phase 6.4 P5 planning]_

- **Set up the two P6 approval prerequisites before go-live.** Run the P6 migrations (`AddSalesBranchCompletedAtIndex`, `AddApprovalPinAndVoidRequestedBy`) before starting the new backend, and have every manager and admin set their approval PIN from the user menu: until someone at a branch has a PIN, nobody there can void. Steps in `docs/frontend/pos-till-setup.md` §6. _[Phase 6.4 P6 E]_

- **Set up the P7 prerequisites before go-live.** Run the two P7 migrations, in order (`AddProductUnitInspectionStatus`, then `CreateSaleReturns`), before starting the new backend; every return needs a manager's or admin's PIN, as voids do. How returns, refunds outside the system, the two-copy slips and Phones to check work at the till: `docs/frontend/pos-till-setup.md` section 7. _[Phase 6.4 P7 G]_

- **Go-live: a cash count with a daily opening and closing balance.** **P9 delivered** (PRs #50–#54; planning doc section 8 "P9 as built"): one opening and one closing balance per branch per Colombo day. Closing figures and the full summary are saved with the day and viewable from Sales → Cash days; no printed day summary is needed. Still deferred (P9-24): multiple till or cashier sessions, shift handover, cash-in/cash-out entries, denomination or blind counts, a PIN on close, and editing or reopening a closed day. There is no physical cash drawer to open; this is the count, not the hardware. _[go-live review after Phase 6.4 P7, narrowed P9 planning]_

- **Go-live: credit sales.** Today a sale completes only when fully paid (`amount_paid` must equal `total`). Some customers buy on credit: the sale completes with a balance owed, later part payments are recorded against it, and the shop needs each customer's balance and a statement. Needs a customer balance model (also the base for store credit, see "Store credit" under Deferred features), a payment-on-account flow at the till, and how a return on a credit sale reduces what is owed instead of refunding cash. Its own phase. _[go-live review after Phase 6.4 P7]_

- **Credit sales must add cash repayments to the expected cash.** P9's expected cash at close counts cash sales, cash refunds and cash handed back for voids (planning doc section 8 P9-5). A credit sale completes with no CASH payment, so it adds nothing, which is right; but a later repayment taken in cash is cash in the box on the day it is taken, and the daily close will come out over unless the credit sales phase adds it to the expected figure, dated by when it was taken. P9 keeps the summary query in one place (`CashDaysService`) so this is one more term there. _[Phase 6.4 P9 planning]_

- **Inventory intake / phone purchase screen must record the cash paid out.** `POST /phone-purchases` (buying a phone outright) records `total_amount` but no tender, and has no screen (Swagger only). The shop pays the seller from the cash box, and P9's expected cash (planning doc section 8 P9-5) knows nothing about it, so until the screen exists a phone purchase made through Swagger makes the daily count come out short by that amount (write it in the close reason). When the intake or phone purchase screen is built, record how the purchase was paid and subtract cash payouts from the expected cash, dated by when they were made. _[Phase 6.4 P9 planning]_



- **Go-live: inventory intake.** Stock can't be brought in properly today. Needs: **suppliers** as records (beyond the external-supplier lines); a **goods received note (GRN)** against a supplier that adds stock, with costs, and creates IN_STOCK phones with their IMEIs (the "No supplier stock intake with IMEIs" entry under Deferred features is part of this); **stock adjustments** with a reason and a history (the `stock_adjustments` entry under Deferred infrastructure), replacing the absolute `PATCH /stock/:id` (see its lost-update entry under Bugs); and **opening stock** for go-live, including each phone's IMEI, entered once before the first sale. The same phase handles returning faulty phones to their supplier (see "Faulty returned phones" under Deferred features). Its own phase, ahead of go-live. _[go-live review after Phase 6.4 P7]_

- **No way to clear an approval PIN on a production backend.** Clearing a forgotten or locked PIN (`DELETE /users/:id/approval-pin`) has no screen until Phase 6.8 and is done through Swagger, but `backend/src/main.ts` serves Swagger only when `NODE_ENV !== 'production'`. The same applies to the other Swagger-only admin tasks (branch address and phone above, `PATCH /branches/:id`). Fix, whichever comes first: the Phase 6.8 user screens, or a documented admin route for production (an authenticated `curl` with the admin's `access_token` cookie, or Swagger behind admin auth). Until then a locked PIN still unlocks itself after 15 minutes, another manager or admin can approve, and a forgotten PIN is cleared with the **SQL fallback** in `docs/frontend/pos-till-setup.md` §6.4 (one `UPDATE users … WHERE email = …` that clears the hash, set time, count and lock). That bypasses the audit log, so the clear is written down by hand (who, for whom, when, why). _[Phase 6.4 P6 E]_

- **Production CORS allows no origin.** **Go-live blocker.** `backend/src/main.ts` sets `origin: ['http://localhost:5173']` in development and `false` otherwise ("tighten for production later"), so a frontend served from any other origin can't call a production backend. Fix with the production hosting setup: the real POS origin from the environment, or the frontend and API behind one origin (reverse proxy). Not P6-specific; found while writing the P6 go-live steps. _[Phase 6.4 P6 E]_

- **Login has no per-account lockout.** `POST /auth/login` now has its own limit per client IP (`LOGIN_THROTTLE_LIMIT` per `LOGIN_THROTTLE_TTL_SECONDS`, default 20 per 15 minutes; `docs/backend/auth.md` "Login rate limit"), on top of the global limits. Still missing: nothing counts failures per account, so guessing spread across many addresses isn't slowed, and nothing locks an account after repeated failures (the approval PIN has a lockout; passwords don't). The per-IP limit is also counted in memory in each process (several backend instances multiply it), and it depends on the production `TRUST_PROXY`: with `false` behind a load balancer, every client shares one login allowance. Related: "API rate limit is per IP" (Bugs), "The global rate limit isn't configurable" (Test-environment friction) and "Choose the production `TRUST_PROXY` value". Fix: a failed-attempt count and temporary lock per account and per account-and-IP pair, without revealing whether the email exists. _[PR #65 audit, login rate limit]_

- **Choose the production `TRUST_PROXY` value.** The backend now reads the client IP only from `req.ip`, which follows `X-Forwarded-For` through the proxies `TRUST_PROXY` trusts (`docs/backend/auth.md`, "Client IP and trusted proxies"), and production refuses to start unless `TRUST_PROXY` is set explicitly. `false` is right for a backend clients reach directly but, behind a load balancer or CDN, makes every client the proxy's address: one shared throttle allowance, and the proxy's IP in the audit log and on sessions. The value depends on the deployment topology, which isn't settled: `docs/architecture.md` plans the backend on "AWS EC2 or ECS", `docs/frontend/api-integration.md` mentions the backend "on ALB", and whether API traffic also passes through CloudFront isn't decided. Fix with the production hosting setup: set `TRUST_PROXY` to the proxies' addresses (preferred) or the exact hop count, and make sure the backend is reachable only through them. Related: "API rate limit is per IP" under Bugs. _[PR #65 audit, trusted-proxy config]_

- **Production must set `NODE_ENV=production` explicitly.** `backend/src/config/env.validation.ts` defaults `NODE_ENV` to `development`, so a production backend started without it runs as development: `validateEnv` doesn't require `COOKIE_SECURE=true` or an explicit `TRUST_PROXY` (it does once `NODE_ENV=production`), `backend/src/main.ts` serves Swagger, and CORS and logging take their development settings. Fix with the production deployment: set `NODE_ENV=production` in its environment, and decide whether `NODE_ENV` should stop having a default. _[PR #65 audit, COOKIE_SECURE enforcement]_
